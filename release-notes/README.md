# GitHub Release 更新说明

每次发布都在此目录新增一份与 tag 同名的 Markdown 文件，例如发布 `v1.0.39` 时创建 `release-notes/v1.0.39.md`。该文件和版本号一起提交；GitHub Actions 只会读取 tag 中的同名文件作为 Release 的标题和正文。

这不是按时间持续追加的 `CHANGELOG.md`。每份文件只描述一个版本，方便发布前审阅、发布后追溯和重跑 CI。

## 文件格式

首行必须是版本核心价值的标题注释，不能为空。它会渲染为 GitHub Release 标题的一部分，但不会出现在正文中：

```md
<!-- title: Cursor 使用体验优化 -->

## 重点更新

**Cursor 的额度与用量界面更简洁**

减少额外的状态说明与提示，让额度、用量等关键信息更集中、更容易浏览。

### 体验优化

- 统一 Cursor 与其他服务的状态展示，减少多余提示。
- 优化统计卡片的数值排版，阅读更直接。

<details>
<summary>安装说明</summary>

- 推荐下载 **`CCBar.dmg`** 安装。
- `CCBar.app.zip` 与 DMG 内容相同，可作为备用下载。

</details>
```

上例在 GitHub 中会显示为 `CCBar v1.0.39 · Cursor 使用体验优化`，并将安装说明默认折叠。若本版没有用户可感知功能，标题应明确写为“内部维护”，正文说明这一事实，不能虚构稳定性、性能或功能收益。

## 撰写规则

- 基于上一个 `v*` tag 至当前版本的真实代码、提交和文档撰写；必要时以 diff 为准，不只复述 commit message。
- 首屏先用一句话说明用户得到的价值，再按非空分类列出“新增功能”“问题修复”“体验优化”“注意事项”。小版本通常只需 1～4 条。
- 每条说明用用户语言表达结果，不写 commit hash、文件名、内部模块、重构过程、CI、测试或版本号变更。
- 仅当用户需要操作、兼容性有影响或已有数据可能变化时，才新增“注意事项”；不要把无关技术信息塞进正文。
- 每版都保留“安装说明”折叠区；如安装方式或产物有变化，按实际情况更新。
- 截图只用于新增或明显改变界面的版本，并且必须是本版真实界面截图；普通修复无需为了装饰添加图片。
