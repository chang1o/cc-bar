## 0. 页面核心需求（作为验收基准）

官方只给「已用百分比」，本页要回答：

1. 当前周期实际烧了多少 Tokens / API 等值费用；

以下所有问题都以此为基准评级。

## 2. P0 问题详情与修复方案

### P0-1 受限重建与增量扫描的 watermark 竞态 → 当前周期双计

**机制**（`Core/Usage/UsageService.swift:161`、`:483`）：
受限重建用 `previous: [:]` 从零扫最近 8 天日志并清桶重灌，但**不推进主扫描 watermark**（`cachedScanState`）。凡是「上次 scanNow 之后、重建之前」新写入的日志条目：重建灌入一次，随后的 scanNow 按旧 watermark 又当新条目 ingest 一次 → **双计**。额度刷新（分钟级）与用量扫描（默认 5 分钟）之间总有空窗，属常态触发；双计要等下一次分区变化触发的重建（最长约 5 小时）才被清桶纠正——正好解释「数字虚高、过阵子又正常」。

现有测试只覆盖「连续重建幂等」，没有覆盖「重建 → 常规增量扫描」序列，所以漏网。

**修复方案（推荐）**：把受限重建改为「先 drain 再重灌」——
1. 重建开始时，先以当前 watermark 跑一次与 `runScan` 相同的增量扫描并正常提交（推进 `cachedScanState`）；
2. 然后再清桶、按窗口重扫重灌。
这样重灌完成后不存在「watermark 之前未入账」的条目。备选方案是把重建扫描产出的 file-state / seenMessageIds 合并回 `cachedScanState`，改动更小但合并语义（offset 取 max、seen 并集、generationID 保持）容易出错，不推荐首选。

**回归测试**：构造「ingest 条目 E（watermark 未推进）→ rebuildRange → 再以含 E 的增量结果 ingest」序列，断言 E 只计一次。

### P0-2 跨窗口的已完成周周期被逐日削减

**机制**（`Core/Usage/UsageService.swift:151` + `:161` + `:205`）：
`affectedCycleIDs` 按**区间相交**（`endAt > now-8d && startAt < now`）圈定要清桶重灌的周期，但重灌扫描只覆盖最近 8 天（Claude 按文件 mtime，Codex 按最近 8 天日期目录）。一个周周期 `[S, S+7d]` 在 `now ∈ (S+8d, S+15d)` 期间每次受限重建（一天数次）都会被清桶，再只灌回落在扫描窗口内的条目 → **周期开头的用量一天天消失**，出窗口后永久固化（watermark 认为条目已见过，不会再补）。5 小时周期同理，暴露窗口在结束后第 7.8~8 天之间。这是历史曲线「数字随时间缩水」的直接来源。

**修复方案（推荐）**：扫描窗口下限改为
`dateFrom = min(now - 8d, affected 周期中最早的 startAt)`，
Claude 的 `minimumMtime` 与 Codex 的日期目录天数同步使用该值（周周期最多多扫 7 天，成本可接受）。备选：affected 集只收「完整落在扫描窗口内」的周期，跨界完成周期不清不灌——改动更小，但周期边界事后被修正的场景会失去重算机会。

**回归测试**：构造 startAt 早于扫描窗口的已完成周期 + 窗口内只含部分条目的扫描结果，断言重建后该周期总量不缩水。

### P0-3 历史清理把两个真实相邻周期并成一条

**机制**（`Core/Storage/QuotaCycleStore.swift:294` `isResetDriftContinuation`，配合 `:642` `closeOverlappingCycles`）：
两个缺陷叠加——

1. **1 秒截断伪造「残片」签名**：新周期 startAt 由它自己的 `resets_at - 窗口长` 推出，与前一周期 `scheduledEndAt` 之间有 ±1~3 秒独立抖动。当它落在前一周期 scheduledEnd 之前 1 秒时，`closeOverlappingCycles` 把前一周期 endAt 截短 1 秒 → 前一周期从此满足「endAt < scheduledEndAt」+「与后一周期相邻 ≤1s」，在**每次启动**的清理里都成为漂移合并候选。
2. **百分比判据用错了值**：`usageDidNotReset` 拿 `later.latestUsedPercent`（后一周期**清理时刻的最新值**）与前一周期终值比较。后一周期用量爬到与前一周期终值相差 <10 个百分点的任意时刻，只要 App 恰好在此时启动做清理，两个真实周期就被并成一条，且 `mergingContinuationAllowanceSegments` 会把两段额度段焊成一段，**不可逆、无法从日志重建**。

**本机实证**：`quota-cycle-history.json` 26 条记录中，异常计数与 GPT 报告完全一致——`firstSampleAt < startAt` 4 条、额度段先于周期开始 4 条、多 `initial` 段 5 条、`lastSampleAt > endAt` 3 条。其中 4 条 Claude 5 小时记录（08-11、08-13、08-14、08-15）各自内嵌了一个**完整的前一 5 小时窗口的 initial 额度段**（如 08-15 记录 `[10:29:59→15:29:59]` 内含 `[05:30→10:30] max=47%` 的前周期段）。这 4 条属旧版清理规则造成的历史固化损伤（v4 重建修不了错误边界），但现行代码在上述两个缺陷下**仍会继续制造新的合并**。

**修复方案（推荐，两处都改）**：
1. `isResetDriftContinuation` 增加最小截断量门槛：`earlier.scheduledEndAt - earlier.endAt > resetJitterTolerance (60s)` 才视为疑似漂移残片——真实漂移截断量为分钟级，边界抖动只有 1~3 秒，量级差可靠区分；
2. `closeOverlappingCycles` 对重叠 ≤ `resetJitterTolerance` 的情况不截断（同源抖动，不是真实重叠）；
3. （可选加固）百分比判据改用后一周期**首个采样时刻的 percent**（需在记录/段上留存首采样 percent，或用首段 `firstSampleAt` 时的值），而非 `latestUsedPercent`。
4. （可选，P2）为已固化的 4 条损伤记录加一次性拆分迁移：检测「多 initial 段且首段跨度 ≈ 整窗口」→ 拆回两条。若不做，需接受这 4 条历史失真并在文档注明。

**回归测试**：相邻两周期、后者 startAt 落在前者 scheduledEnd 前 1 秒、后者最新 percent 与前者终值相差 <10 → 断言清理后仍是两条记录。

## 3. P1 问题详情与修复方案

### P1-4 受限重建漏扫 Codex 平铺归档目录（GPT#3，已验证）

`Core/Usage/UsageService.swift:210` 给 `~/.codex/archived_sessions` 拼接了 `YYYY/MM/DD`，但本机验证该目录是**平铺结构**（`rollout-*.jsonl` 直接在根下，且存在 08-17 新归档文件）。只要 `sessions` 的日期目录存在，roots 非空、不触发全量兜底 → 归档会话条目在每次受限重建的清桶重灌中丢失。另有同族问题：`codex resume` 续用超过 8 天前开始的会话时，新条目写在旧日期目录里，同样落在 roots 之外。

**修复方案**：Codex 受限重建放弃日期目录法，与 Claude 对齐——扫描 `sessions` / `archived_sessions` 两个根目录并用 `minimumMtime = dateFrom` 过滤（`JSONLDirectoryEnumerator` 已支持该参数，给 `CodexJSONLScanner.scan` 透传即可）。目录枚举成本低，且同时修掉 resume 旧会话漏扫。

### P1-5 Claude 账号键恒定 → 切号串数据（GPT#4，已验证）

`QuotaHistoryStore.swift:55` `claudePrimary()` 恒返回 `"claude:primary"`；`AppState.swift:996` 能通过 email 识别 Claude 账号切换并清额度缓存，但 `AppState.swift:1257` 写入周期时 key 不变 → `updateAccountSegments` 永远不会关闭旧账号时间段，两个账号的周期记录与本机用量互相归属。与产品文档「账号切换按时间段隔离」直接矛盾。Codex 在 `accountId` 缺失（PAT 身份回填前）时同样退化为常量 `"codex:primary"`。

**修复方案**：`claudePrimary` 带上账号标识（如 email 规范化 hash），并做一次性迁移：载入时把旧 `"claude:primary"` 记录/段重写为当前账号键（历史无法区分，归入当前账号并接受一次性误差）；视图 `accountKey(for:)` 同步。Codex 侧在 accountId 从缺失变为已知时，可将 `"codex:primary"` 段收口并以新键开段（现有 `updateAccountSegments` 机制天然支持，只需确认回填后 key 变化会走到）。此项涉及数据迁移，建议单独出一小节设计再动手。

### P1-6 扫描失败静默清空 → 落盘残缺结果（GPT#5，已验证）

`CodexJSONLScanner.swift:229` / `ClaudeJSONLScanner.swift:114`：`JSONLLineReader.read` 失败只跳过文件，不上报；根目录不可达时枚举结果为空同样无感。受限重建（`CycleUsage.swift:327`）先清桶再灌，失败场景下会把**空或残缺的结果持久化**。虽然可通过设置页「强制重算」人工恢复，但用户无从知道需要恢复。

**修复方案**：
1. 扫描 `Result` 增加 `failedFileCount`（读取失败 + 根目录不可达计数）；
2. `commitCycleAggregation` 在 `failedFileCount > 0` 时**跳过清桶重灌、保留旧桶**，写 `lastError` 提示；
3. 常规增量扫描同样上报该计数到 `lastError`（增量路径不清桶，风险低，仅提示）。

## 4. P2 / P3 问题（择机修复）

- **P2-7 Y 轴无标签**：`Main/CycleStatsView.swift:325` 对 `automatic(desiredCount:4)` 连续轴用 `value.as(Int.self)`，费用峰值低于几美元时刻度为小数 → 全部返回 nil，一个标签都不显示（`StatsView.swift:1579` 同写法能工作是因为刻度是显式整数数组）。改 `value.as(Double.self)` 再格式化。
- **P2-8 预估无置信门槛**：`forecastConfidence`（`CycleUsage.swift:157`）已实现但 UI 未使用。observed 仅 0.5% 时 `×100/0.5` 的爆炸值直接以 24pt 大字上 KPI 卡，数小时后回落，观感即「统计 bug」。建议 `.early` 档显示「早期估算」标记或降级为 `—`。
- **P2-9 写入路径的周期合并**：`QuotaCycleStore.swift:489` 第三重匹配（`endAt > sampledAt` 且非 extraReset）无任何时间接近性约束。Codex 周窗口提前重置 + 旧用量 <5% 且回落不足 3 点时，旧记录的 `scheduledEndAt` 被整体搬到新窗口，两个真实周期在线合并。修法与 P0-3 同思路：给该匹配加 `|candidate.scheduledEndAt - scheduledEndAt|` 上限（如 ≤ 数分钟量级的漂移容差）。
- **P3-10 空态闪现**：周期到点后到下次刷新成功前 `isCurrent()` 无命中，KPI 卡从满数据跳回空态。本机数据显示 Claude 5h 窗口过夜可空 11 小时（服务端整夜返回旧 `resets_at`）。建议空态区分「等待新周期」与「从未有周期」，或展示刚结束的周期并标注已结束。
- **P3-11 孤儿桶**：清理删除周期记录后其桶留在聚合器，会话内不可见（无害），但下次启动 `rollupCycleIDs.isSubset` 校验失败触发一次全量重建（转圈补算）。可在受限重建时顺带丢弃 cycleID 不在现存记录中的桶。
- **P3-12 渲染性能**：`summaries()` 每帧被 KPI ×4 + 历史面板调用共 ~8 次，每次对全部桶 × 周期分组重算。数据量增长后可考虑按 `(records, buckets)` 缓存。
