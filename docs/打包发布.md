# 打包发布

本文只记录 cc-bar 当前工程的打包步骤。工程产物名为 `CCBar.app`，版本号来自 Xcode build settings：`MARKETING_VERSION`（当前见 `ccbar.xcodeproj/project.pbxproj`），`CURRENT_PROJECT_VERSION = 1`。

## 0. 默认方式：`scripts/build.sh`（推荐，日常都用这个）

日常打包分发**只用**仓库自带的脚本，不要走下面第 1/2/4 节的 Archive 流程——那套会引入本机的 "Apple Development" 开发证书，产物只能在本机运行，拷给别人会打不开，也没有必要为了自用而覆盖 `/Applications` 里正在跑的安装。

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer   # 一次性，确保指向完整 Xcode
./scripts/build.sh                                                 # 产物: dist/CCBar.app.zip
```

- 脚本内部用 `CODE_SIGNING_ALLOWED=NO` 做 Release 构建，工具链自动 ad-hoc 签名，任意 Mac 可运行，不需要付费证书或公证。
- 产物固定在 `dist/CCBar.app.zip`（`dist/` 已 gitignore，不进版本库）。
- 想验证打包是否正常，解压到临时目录看，不要直接替换 `/Applications/CCBar.app`。
- 详见 [README.md「从源码构建」](../README.md#从源码构建)。

### GitHub Actions 自动发布

仓库配置了 [.github/workflows/release.yml](../.github/workflows/release.yml)：推送 `v` 开头的 tag（如 `v1.0.0`）后，GitHub 的 macOS runner 会自动执行 `scripts/build.sh` 并把 `CCBar.app.zip` 挂到同名 GitHub Release。

runner 镜像默认预装的 Xcode 版本可能落后于本地(如 macos-15 runner 默认 Xcode 16.4，SDK 停在 macOS 15.5)，用旧 SDK 编译出的 App 在新版 macOS 上会渲染成旧一代系统外观，和本地新 Xcode 编译的效果不一致。workflow 里用 `maxim-lobanov/setup-xcode@v1` 把 Xcode 固定为 `latest-stable`，跟随 runner 镜像自动使用当前最新稳定版，避免这个问题。

```bash
git push origin main
git tag v1.0.0          # 版本号要和 project.pbxproj 里的 MARKETING_VERSION 一致，且改动已提交
git push origin v1.0.0
```

进度和日志在仓库的 Actions 页查看。CI 产物与本地脚本产物等价（同为 ad-hoc 签名）。

**更新日志放在哪**：GitHub Release 的描述（Release notes）就是更新日志，由 `generate_release_notes: true` 根据这个 tag 和上一个 tag 之间的所有 commit message 自动生成，仓库不另外维护 CHANGELOG.md 文件——commit message 写清楚即可。

> 版本号从 `v1.0.0` 重新起算。仓库早期用过不带 `v` 前缀的 `0.x.y` 裸版本号 tag，属于历史遗留，新发布不再接续那条线。

完整的「提交代码 → 版本号+1 → 构建打包」标准流程（含 AI 代执行的固定步骤）见 [CLAUDE.md](../CLAUDE.md) 的「标准发布流程」一节。

下面第 1–4 节保留给需要 **Developer ID 签名 + 公证** 发布给他人（例如上架、企业分发）的场景，日常迭代不需要看。

## 1. 打包前检查（仅 Developer ID 场景需要）

1. 用完整 Xcode 打开 `ccbar.xcodeproj`，不要只安装 Command Line Tools。
2. 在 Xcode 左侧选中项目 `ccbar`，进入 target `ccbar` 的 `Signing & Capabilities`。
3. `Team` 选择你的 Apple Developer 账号。
4. `Bundle Identifier` 保持 `com.nanvon.ccbar`。如果这个 id 已被占用，改成你自己的唯一 id，例如 `com.yourname.ccbar`。
5. 顶部 scheme 选择 `ccbar`，运行目标选择 `Any Mac` 或本机 Mac。

## 2. 只给自己用（不推荐，优先用第 0 节脚本）

1. Xcode 菜单选择 `Product` -> `Archive`。
2. Archive 完成后会打开 Organizer。
3. 选择刚生成的 archive，点击 `Distribute App`。
4. 选择 `Copy App`，导出 `CCBar.app`。
5. 把 `CCBar.app` 拖到 `/Applications` 后启动。

这种方式签名用的是本机 "Apple Development" 证书，只适合自己电脑使用，发给别人时对方会遇到 Gatekeeper 的"无法验证开发者"提示；且第 0 节脚本已覆盖这个场景，一般不需要走 Archive。

## 3. 发给别人用（需要 Developer ID 证书）

需要 Apple Developer 账号和 Developer ID 证书。

1. Xcode 菜单选择 `Product` -> `Archive`。
2. Organizer 中点击 `Distribute App`。
3. 选择 `Developer ID`。
4. 选择 `Upload` 让 Apple notarize。
5. notarization 成功后导出 `CCBar.app`。
6. 压缩成 zip 后发布，例如：

```bash
ditto -c -k --keepParent CCBar.app CCBar.app.zip
```

## 4. 命令行归档（仅 Developer ID 场景需要）

如果要用命令行走 Developer ID 流程，先确认 `xcodebuild` 指向完整 Xcode：

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

归档：

```bash
xcodebuild archive \
  -project ccbar.xcodeproj \
  -scheme ccbar \
  -configuration Release \
  -archivePath build/CCBar.xcarchive
```

Developer ID 导出：

```bash
xcodebuild -exportArchive \
  -archivePath build/CCBar.xcarchive \
  -exportPath build/export \
  -exportOptionsPlist ExportOptions-DeveloperID.plist
```

导出成功后，app 在 `build/export/CCBar.app`。

## 5. 常见问题

- 如果 `xcodebuild` 提示 active developer directory 是 Command Line Tools，说明没有切到完整 Xcode，按第 4 节先执行 `xcode-select`。
- 如果签名失败，先回到 Xcode 的 `Signing & Capabilities` 检查 Team 和 Bundle Identifier。
- 如果设置里的「开机自动启动」提示 `Operation not permitted`，通常是当前 App 不是签名导出的 `.app`，或没有从 `/Applications/CCBar.app` 启动。用第 0 节的 `scripts/build.sh` 重新打包，解压 `dist/CCBar.app.zip` 后手动确认再拖到 `/Applications`（会覆盖已有安装，替换前先确认这是你想要的）；同时检查「系统设置 -> 通用 -> 登录项与扩展」里 CCBar 是否被禁用。
- 如果只是自己使用，不需要 notarization；如果发给别人长期使用，建议走 Developer ID + notarization。
