> 配套需求见 [草案-用量统计增强与对话明细-需求.md](草案-用量统计增强与对话明细-需求.md)。

## 1. 现状摘要（改动基线）

数据流（见 [技术实现.md](技术实现.md) §7）：

```
Scheduler → UsageService.scanNow()
  → ClaudeJSONLScanner / CodexJSONLScanner（Task.detached utility，增量 mtime+offset）
  → [UsageEntry]（逐条：app/model/day/timestamp/四项 token/costUSD）
  → UsageAggregator（@MainActor @Observable，(day, app, model) 桶）
  → 持久化：ScanCache（watermark + seenMessageIds + pricingFingerprint）
           UsageRollupCache（usage-rollup.json，全部桶）
  → StatsView 直接读 aggregator.snapshot() 过滤聚合
```

关键既有机制（本方案复用，不重造）：

- `Pricing.fingerprint(knownModels:)`：价格表内容指纹，调用方从当前聚合桶推导已知模型集合；内容变了自动全量重扫。
- `UsageService.forceRescan()`：清内存 + 空 ScanState 重扫。
- Claude 跨文件按 `message.id` 全局去重（seen 集合，cap 20000）。
- Codex `input_tokens` 含 cache，扫描时已扣成 billable input。

## 2. 总体设计

新增「会话」维度，与现有「天」维度**并行聚合**，一次扫描同时产出两套桶：

```
scanner 产出 UsageEntry（新增 sessionKey / requestCount 字段）
  ├─ UsageAggregator            (hourBucket, app, model)          → usage-rollup.json（改造：day→hour，加 requestCount）
  └─ SessionAggregator（新增）   (sessionKey, day, model) + 会话档案 → session-rollup.json（新增）
```

- 时间粒度从 day 细化到 **hour**（只为 F3 当天小时趋势）；按天视图由小时桶向上累加，UI 无感。
- 会话档案（SessionInfo）与会话用量桶分开存：档案记录标题 / 路径等静态信息，桶记录 (会话, 天, 模型) 的用量，支持「范围内消耗」过滤。
- 结构变更靠 **schemaVersion** 触发全量重扫（复用 pricingFingerprint 同一判断路径），不写旧数据迁移代码。

## 3. 数据模型变更

### 3.1 `Core/Usage/UsageModels.swift`

```swift
// UsageEntry 新增：
var sessionKey: String        // Claude = sessionId；Codex = session_meta.id（缺失时用文件名兜底）
var requestCount: Int         // 恒为 1，聚合时累加

// UsageBucket：day: Date（当天 0 点）→ hourStart: Date（本地时区整点）；新增 requestCount: Int
// Codable 的 CodingKeys 同步改；不做旧字段兼容（schemaVersion 会触发重扫）。
// 提供便捷属性 var day: Date { UsageDay.startOfDay(for: hourStart) } 供按天聚合。

// UsageTotals 新增 requestCount: Int = 0，add(_:) 同步累加。
```

### 3.2 会话模型（新文件 `Core/Usage/SessionModels.swift`）

```swift
/// 会话静态档案。首次见到该会话时创建，此后只更新 lastAt / title（若仍为空）。
struct SessionInfo: Sendable, Codable, Equatable {
    var key: String            // 全局唯一：加前缀 "claude:" / "codex:" 防两家撞 id
    var app: UsageApp
    var filePath: String       // 会话源 JSONL 绝对路径（详情页逐请求解析用；Claude 取主文件）
    var project: String        // cwd（完整路径，UI 自行取尾段）
    var gitBranch: String?     // 仅 Claude
    var title: String?         // 首条用户消息截断（≤80 字符，去换行）；nil = 无标题
    var firstAt: Date
    var lastAt: Date
}

/// (会话, 天, 模型) 用量桶。天用本地 0 点（会话维度不需要小时粒度）。
struct SessionUsageBucket: Sendable, Codable, Equatable {
    var sessionKey: String
    var app: UsageApp
    var day: Date
    var model: String
    var inputTokens: Int
    var outputTokens: Int
    var cacheReadTokens: Int
    var cacheCreationTokens: Int
    var requestCount: Int
    var costUSD: Decimal              // 编解码走既有 Decimal<->String 模式
    var inputCostUSD: Decimal         // 四项成本分列，详情页「成本明细」直接读，避免二次计价
    var outputCostUSD: Decimal
    var cacheReadCostUSD: Decimal
    var cacheCreationCostUSD: Decimal
}
```

体积估算：数千会话 × 平均 1–2 活跃天 × 1–2 模型 ≈ 万级桶，JSON 约 2–4 MB，与现有缓存同量级，可接受。保护：持久化时按 `lastAt` 只保留最近 **10000** 个会话的档案与桶。

### 3.3 成本四项分列（`Core/Usage/Pricing.swift`）

新增：

```swift
struct CostBreakdown: Sendable { var input, output, cacheRead, cacheCreation: Decimal
                                 var total: Decimal { input + output + cacheRead + cacheCreation } }
static func costBreakdown(model:input:output:cacheRead:cacheCreation:at:) -> CostBreakdown
```

现有 `cost(...)` 改为调用 `costBreakdown(...).total`，保证两条路径永远一致。扫描器改用 `costBreakdown`，`UsageEntry` 增加四项成本字段（或直接由 scanner 填进 SessionUsageBucket，二选一，推荐前者简单）。

> 注（远端价格目录改动后已生效）：`Pricing.cost(...)` 的返回类型已经是 `Decimal?`（`nil` = 未定价，区别于真实 $0），`UsageEntry.costUSD` 同步是 `Decimal?`；`CostBreakdown`/`costBreakdown(...)` 落地时需要同样返回可空类型或提供等价的「未定价」标记，不要把 nil 悄悄折成 0 再放进 `total`，否则会破坏未定价可识别性。`UsageBucket`/`SessionUsageBucket` 等聚合结构可以继续用非可空 `Decimal`（未定价按 0 聚合，识别靠 `Pricing.hasPrice(model:)` 现查，不需要在聚合结构里再存一份可空状态）。

## 4. 扫描器改造

### 4.1 Claude（`ClaudeJSONLScanner.swift`）

每行顶层已含 `sessionId` / `cwd` / `gitBranch`（assistant 与 user 行都有），改动：

- `parseAssistantLine` 额外提取 `sessionId`、`cwd`、`gitBranch`，随 ParsedAssistant 传出；entry 的 `sessionKey = "claude:" + sessionId`。
- 标题提取：解析到 `type == "user"` 且 `isSidechain != true` 的行时，若该 sessionId 尚无标题（查本次扫描的会话表 + 已持久化档案），取 `message.content`：字符串直接用；数组取第一个 `{"type":"text"}` 项的 `text`。规则：跳过以 `<` 开头的内容（`<command-name>` 等注入指令）；去首尾空白、换行折叠为空格、截断 80 字符。**user 行解析放在现有 assistant 判断之前用 type 分派，不改变 assistant 主路径。**
- 会话归属：entry 归属其所在行的 `sessionId`（subagent 文件有自己的 sessionId，自然成为独立会话，需求 §7-3 已确认口径）。message.id 全局去重逻辑**不变**——同一 id 只会计入首次见到的那个会话。
- `filePath`：会话首次出现时记当前文件路径。

### 4.2 Codex（`CodexJSONLScanner.swift`）

- 新增解析 `type == "session_meta"`：取 `payload.id`（sessionKey = `"codex:" + id`）、`payload.cwd`。**增量扫描从 offset 续读时读不到文件头**，因此把已解析的 sessionKey / cwd / 标题完成标记存进 `ScanFileState`（见 §5）；老文件（升级前已有 watermark 的）在全量重扫后自然补齐。文件名含 uuid，session_meta 缺失时从文件名正则兜底。
- 标题提取：首条 `event_msg` 且 `payload.type == "user_message"` 的 `payload.message`，同样的清洗与 80 字符截断规则。
- `token_count` 事件生成 entry 时带上当前文件的 sessionKey，`requestCount = 1`。

### 4.3 会话聚合（新文件 `Core/Usage/SessionAggregator.swift`）

对照 `UsageAggregator` 写一个 `@MainActor @Observable` 的会话聚合器：

- `infos: [String: SessionInfo]`、`buckets: [SessionBucketKey: SessionUsageBucket]`（key = sessionKey+day+model）。
- `ingest(entries:sessionMeta:)`：累加桶、创建/更新档案（lastAt 取 max，title 只在为空时补）。
- 查询接口（供 UI）：
  - `sessionRows(app: UsageApp?, model: String?, from: Date, to: Date) -> [SessionRow]`：范围内过滤桶 → 按 sessionKey 分组求和 → join 档案。
  - `sessionDetail(key: String) -> (SessionInfo, totals: UsageTotals, costBreakdown, perModel: [...])`：全生命周期聚合。
- 由 `UsageService` 持有并在 `runScan` 中与 UsageAggregator 一起 ingest / 持久化。

### 4.4 逐请求按需解析（新文件 `Core/Usage/SessionRequestLoader.swift`，P1）

详情页点开「请求明细」时调用，`Task.detached(priority: .userInitiated)`：

- Claude：全量读 `SessionInfo.filePath`，复用 scanner 的行解析（把 `parseAssistantLine` 提为 internal 复用），同一 message.id 按「stop_reason 非空优先」取一条（与扫描逻辑一致），产出 `[RequestDetail]`（时间 · 模型 · 四项 token · CostBreakdown）。
- Codex：全量读文件，`turn_context` 跟踪模型 + `token_count` 产出记录。
- 结果仅内存展示，不持久化。单文件通常 < 20 MB，解析亚秒级。

## 5. 持久化与失效

### 5.1 `Core/Storage/ScanCache.swift`

- `ScanState` 新增 `schemaVersion: Int`（本次置 **2**；缺失视为 1）。`UsageService.scanNow()` 前置检查：`schemaVersion != 当前` 或 `pricingFingerprint != Pricing.fingerprint(knownModels:)`（`knownModels` 由当前聚合桶推导）→ 走 forceRescan 路径（清两个聚合器 + 空 ScanState）。现有指纹检查逻辑在哪里判断就在哪里加，不新开路径。
- `ScanFileState` 新增（Codex 用）：`sessionKey: String?`、`sessionCwd: String?`、`titleCaptured: Bool`。Claude 不需要（每行自带 sessionId；标题捕获状态由档案里 title 是否为 nil 表达——注意：title 确实提取不到的会话每次增量扫描会再试一次，量小可接受）。

### 5.2 新文件 `Core/Storage/SessionRollupCache.swift`

对照 `UsageRollupCache` 实现：`session-rollup.json`，payload 含 `schemaVersion`、`pricingFingerprint`、`infos`、`buckets`、`updatedAt`。读写均在 detached utility task（跟随 UsageService 现有模式）。写入前执行 §3.2 的 10000 会话裁剪。

### 5.3 `usage-rollup.json`

结构变更（hourStart + requestCount + 四项成本可不存，天桶只需 total costUSD）。由 schemaVersion 触发重扫自动重建，**不写迁移**。

## 6. UI 实现（`Main/StatsView.swift` 及拆分）

StatsView 已 1300+ 行，新增内容按现有 `// MARK:` 风格拆新文件：`Main/StatsOverviewHero.swift`、`Main/StatsTrendPanel.swift`、`Main/StatsBreakdownView.swift`、`Main/SessionDetailSheet.swift`（命名可微调，保持 Main/ 平铺现状）。

### 6.1 Overview 改造

- KPI 区改为：Hero 卡（真实消耗大数字 + 紧凑近似 + 请求数 + 总成本 + delta）一行，下接四项细分卡 + 命中率卡一行（五格网格，命中率卡含进度条）。组件复用 `Panel` / `KPICard` 语汇与 `ccPanel`。
- 细分卡 N/A 逻辑照需求 F1；tooltip 用 `.help()`。
- 数据全部来自 `aggregator.snapshot()` 的现场过滤聚合（现状模式），加模型筛选条件。

### 6.2 筛选

- `@State var modelFilter: String?`；顶部 topBar 加 `Picker`（menu 样式）在 segmented 左侧。选项 = 当前 serviceFilter + rangeBounds 内桶的模型去重排序；切 serviceFilter 时 `modelFilter = nil`；选中项掉出选项时补回（对齐 cc-switch 细节）。

### 6.3 趋势面板

### 6.4 Breakdown 视图

- 侧栏启用 `Breakdown / 明细`（去掉 disabled/opacity），`viewMode` 加 `.breakdown`。
- 列表用 SwiftUI `Table`（工程已用 macOS 14+ API，可用；支持列排序 `sortOrder`），行数据 = `SessionRow`。默认取前 200，底部「显示更多 / Show more」按钮翻倍。
- 行点击（`Table` 选中 + 双击，或行尾按钮）弹 `sheet` → SessionDetailSheet（约 620×540）：分区照需求 F5；逐请求区块 P1 懒加载（`task {}` 触发 SessionRequestLoader，spinner / 错误态）。
- 进入 Breakdown 时 `if lastScanAt 距今 > 60s { Task { await usageService.scanNow() } }`。

### 6.5 扫描状态条（F6）

- topBar 左侧加：`上次扫描 {相对时间}` 次要文字 + `arrow.clockwise` 图标按钮；`isScanning` 时按钮禁用转 `ProgressView`。读 `UsageService.lastScanAt / isScanning`（需把这两个属性纳入 @Observable 可观察，UsageService 目前不是 @Observable —— 最小改法：这两个状态镜像到 AppState 或把 UsageService 标 @Observable，选后者）。

### 6.6 双语与格式

- 新词条全部走 `tr(en, zh)` 就地双语（现状模式），并把词条补进设计风格.md 双语词表。
- token 紧凑格式复用 `StatsFormatter.compactToken`；成本明细里的小额成本新增 `StatsFormatter.costPrecise`（4–6 位小数，参照 cc-switch 详情页 $x.xxxxxx）。

## 7. 性能与并发

- 扫描仍在 detached utility；SessionAggregator 的 ingest 在 MainActor（与 UsageAggregator 同模式，数据量为条目级，现状已验证可行）。
- Breakdown 的 sessionRows 聚合是 O(桶数)，万级桶在 MainActor 现场计算可接受（与现有 filteredBuckets 同模式）；若实测卡顿再谈缓存，不预先优化。
- 逐请求解析、缓存读写全部 detached，主线程只碰结果。
- 小时桶让 usage-rollup.json 行数增至现有 ~10–24 倍，读写仍是毫秒级；不换 SQLite（保持工程无新依赖）。

## 8. 风险与回滚

| 风险 | 应对 |
|---|---|
| 全量重扫一次性成本（升级首启） | 现有 forceRescan 已是同路径；扫描期间 UI 显示旧缓存？——不显示：schema 变更时旧 rollup 直接弃用，KPI 短暂为 0 直至扫描完成（秒级~十秒级），可接受；实施时在 release note 说明 |
| Claude 标题提取撞上非常规 content（纯图片首消息等） | 提取失败即 nil → UI 显示（无标题），不阻塞 |
| Codex 增量续读丢 session_meta | ScanFileState 缓存 sessionKey/cwd（§5.1）；升级即全量重扫，无历史空洞 |
| 会话数暴涨撑大 JSON | 10000 会话裁剪上限（§3.2） |
| 数字对不上（列表合计 ≠ 总览） | 两套桶同源同一批 entries，验收标准 §8-1 强制对账；出现偏差优先查去重归属 |
| 回滚 | 本功能纯本地只读统计，不碰凭据/额度路径；回滚 = 回退代码 + 删除 session-rollup.json（下次扫描按旧 schema 重建） |
