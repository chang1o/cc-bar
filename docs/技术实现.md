## 1. 技术栈

| 层 | 选择 | 备注 |
|---|---|---|
| 语言 | Swift 6 | 严格并发 |
| 工程 | Xcode `ccbar.xcodeproj` | 单 target，标准 macOS App |
| UI | SwiftUI 主、AppKit 辅 | 菜单栏 label / 悬浮窗 panel 走 AppKit |
| 最低系统 | macOS 14 Sonoma+ | 依赖 `MenuBarExtra(.window)`、`@Observable`、`SMAppService` |
| 存储 | UserDefaults + JSON 文件 | 不引入 SQLite |
| 网络 | `URLSession` async/await | 标准库，无第三方依赖 |
| 图表 | `Charts`（SwiftUI） | 用于统计 tab 日趋势 |

整个工程零第三方依赖；钥匙串通过命令行 `security` 访问，避免 Keychain Services API 的多次授权弹窗。

## 3. 应用入口与窗口组合

`CCBarApp.swift` 组装三个 Scene：

1. `MenuBarExtra(.window)`：label 是自绘 NSImage 包装；content 是 `PopoverRootView`。`.task` 内执行 `appState.bootstrap()` 并把 `FloatingPanelController` 与 AppState 绑定，再根据设置同步显示。
2. `Window("CCBar", id: "main")`：主窗口，内部 `MainWindowRootView` 用 TabView 切「统计 / 设置」。
3. `Window("Welcome", id: "onboarding")`：引导窗口，`fixedSize` 禁缩放。

`AppCommands` 通过 `CommandGroup` 注入全局快捷键：

- `⌘,` → 打开主窗口并切到设置 tab。
- `⌘1` → 打开主窗口并切到统计 tab。
- `⌘R` → 调用 `appState.refreshNow()`。

`AppDelegate` 启动时设 `NSApp.setActivationPolicy(.accessory)`，让进程默认不出现在 Dock。冷启动（含 `SMAppService` 开机自启、Dock / 应用程序 / Launchpad / Raycast 手动启动）一律静默，只驻留菜单栏，不自动打开主窗口；用户点 Dock 图标触发 `applicationShouldHandleReopen` 时，通过安装在 `MenuBarLabelRoot` 的 SwiftUI handler 调用 `openWindow(id: "main")`，并先把 `mainTab` 设为 `.stats`；handler 未安装时先记录 pending，避免丢失事件。首次启动由 Onboarding 接管。`MainWindowRootView` 在 `onAppear` / `onDisappear` 里把策略切到 `.regular` / 切回 `.accessory`：只有主窗口（统计 / 设置）打开期间才显示 Dock 图标，Popover 不受影响。

## 4. 全局状态：`AppState`

`@Observable @MainActor`，单例方式由 `CCBarApp` 持有并通过 `.environment` 注入。核心字段：

- 凭据 / 身份：`codexAccount` / `claudeAccount` / `antigravityAccount`；Antigravity 只保存本地接口返回的邮箱与 plan，不保存 OAuth token。
- 额度：主服务统一存于 `primaryQuotaStates[QuotaApp]`，Codex / Claude / Antigravity 计算属性保留为兼容入口；来源为 `api` / `local` / `cache` / `cliFallback`。
- 刷新状态：`QuotaRefreshState`（`lastSuccessAt`、`lastAttemptAt`、`backoffUntil`、`lastError`、`inFlight`、`source`）。
- 显示设置：`SettingsStore.providerDisplaySettings[QuotaApp]` 统一保存全局 / 菜单栏 / 悬浮窗开关；首次读取时迁移旧 Codex / Claude UserDefaults key。统计页服务开关走独立的 `SettingsStore.usageServiceVisibility[UsageApp]`（默认全开，JSON 持久化到 `ccbar.settings.usageServiceVisibility.v1`）：过滤只发生在展示层（`StatsView.filteredBuckets` 等），扫描 / 聚合 / 入库仍全量，重新开启后历史照常出现。
- 今日花费：`codexTodayCost` / `claudeTodayCost` / `piTodayCost` / `opencodeTodayCost`，由 `UsageService.publishTotals()` 写入（Pi / OpenCode 无订阅额度，仅用于 Popover 今日花费合计）。
- UI 协调：`mainTab`（统计 / 设置）、`shouldShowOnboarding`。
- 子系统：`usageService`、`scheduler`、`quotaCache` 内存副本、Claude CLI 兜底冷却 `claudeFallbackBackoffUntil`。

关键方法：

- `bootstrap()`：只执行一次；按顺序加载 quota 缓存 → `UsageService.bootstrap` → 读 Codex 凭据 → 必要时弹 Keychain 引导 → 读 Claude 凭据 → 决定是否展示引导 → 启动 Scheduler → 触发首次 JSONL 扫描（异步不阻塞）。
- `refreshNow()`：用户手动刷新；触发一次额度刷新、JSONL 扫描和服务状态拉取。
- `refreshQuotas(reason:)`：每次刷新(手动 / Scheduler 定时)按 `QuotaRefreshPlan`（由当前 Provider 开关与可见导入账号一次性构造）只刷新已启用的主 Provider 与可见导入账号；关闭 Codex / Claude 后不再进入对应凭据、token 与额度链路。`loadCodex` / `loadClaude` 内部比较 `accountId` / `email`，发现身份变化(例如 cc-switch 外部切换了账号)时清掉旧的额度快照与磁盘缓存，避免出现"新账号 + 旧额度"的错配。可见导入 Codex 账号仍按自身设置独立调度，且只有主 Codex 启用时才可能与主账号镜像。
- `applySettingsChange()`：设置项变化后立即把新间隔灌进 Scheduler。

刷新前置校验在 `beginCodexRefresh` / `beginClaudeRefresh` 中：检查 `inFlight`、`backoffUntil`、周期性触发的 60s 最小间隔。成功后 `storeXxx` 只更新内存快照并标脏持久化文件；`refreshQuotas` / `bootstrap` / 设置操作末尾把标脏文件以不可变 snapshot 一次性提交给 `QuotaPersistenceCoordinator`（actor），编码与原子写移出 MainActor，同一文件一轮最多写一次；coordinator 串行执行并合并写入期间到达的新快照，保证后发的新版本不被较晚完成的旧写入覆盖。失败走 `markXxxFailure`，遇 429 设置 10 分钟退避。

## 5. 凭据读取

### 5.1 Codex

`CodexAuth.load()` 优先读 `$CODEX_HOME/auth.json`（未设置 `CODEX_HOME` 时回落 `~/.codex/auth.json`），解析 `tokens.access_token` / `refresh_token`，再用 `JWT.decode` 解 `id_token` 的 payload 拿邮箱、`chatgpt_plan_type`、`account_id`。

**personal access token 形态**：当 auth.json 没有可用 `tokens.access_token`、但有顶层 `personal_access_token`（形如 `{"OPENAI_API_KEY": null, "personal_access_token": "at-..."}`，即在 ChatGPT Team/Enterprise 后台「访问令牌」创建的 Codex 工作区访问令牌）时，`CodexAuth.load()` 把它当 access_token 返回，并置 `CodexAccount.isPersonalAccessToken = true`。该令牌是不透明字符串、无 JWT、无 `exp` / `refresh_token`：

- 取数时跳过 `CodexTokenRefresher`，直接拿令牌当 Bearer 打 `wham/usage`，不发 `ChatGPT-Account-Id` header（令牌已绑定账号）。
- 身份（`email` / `plan_type` / `account_id` / `user_id`）本地解不出，由 `wham/usage` 响应回填到 `codexAccount`；重读 auth.json 时令牌不变则沿用上次回填，`codexIdentityChanged` 对 PAT 改用 access_token 本身判定账号切换。

`CodexTokenRefresher.ensureFreshAccessToken`：当 JWT `exp` 剩余 < 300s 时 POST 到 OpenAI OAuth token 端点（grant_type=refresh_token，client_id 用 Codex CLI 公开 ID），成功后原子写回 `auth.json`。（PAT 账号不走此路径。）

**Codex 侧保留刷新，但装了三道防撞。** OpenAI 同样对 refresh_token 做重用检测（`refresh_token_reused`），并发刷新会把有效登录搞掉：

1. **进程内串行 + 去重**：`Coordinator` actor 按 `WriteBack.coordinationKey`（`auth.json` / `imported:<id>`）分键维护 `inFlight` Task。AppState 有 4 个入口会调 `ensureFresh*`，合并成一次请求；不同导入账号各自独立，不会互相合流。
2. **发请求前重读存储**：`peekStored(writeBack:)` 再读一次 `auth.json` / `ImportedCodexStore`。若 `codex` CLI 已自行轮换过且新 access_token 还新鲜，直接采用不发请求；即便仍过期，也用盘上最新的 refresh_token 去刷，不拿陈腐副本撞重用检测。
3. **写回失败不吞掉**：此时服务端已经轮换、旧 token 作废，写回失败就意味着盘上留着废票、下次启动登录失效。`persist` 重试一次，仍失败则记 `error` 级日志（category `codex-refresh`）并继续返回本次刷到的 token——它这次会话仍可用，不该因落盘失败让整次取数失败。

`WriteBack.importedAccount(id:)` 指向 cc-bar 自己的 Keychain 条目（`com.cc-bar.codex.imported`），不与任何 CLI 共享，这条路径的刷新本身就没有竞争。

### 5.2 Claude

`ClaudeAuth.load()` 优先读 `~/.claude/.credentials.json`；不存在再调 `security find-generic-password -s "Claude Code-credentials" -w` 读 Keychain。邮箱兜底来自 `~/.claude.json` 顶层 `oauthAccount.emailAddress`。

`ClaudeTokenRefresher.ensureFreshAccessToken`：**只读，不刷新、不回写。**

- 手上的 access_token 未过期（`refreshSkew=30s`）→ 直接用。
- 已过期 → 重读一次凭据存储，期待 Claude Code 已经自己刷过：读到的 access_token 还够用（`adoptSkew=5s`）就采用并更新 `claudeAccount`。
- 重读仍拿不到有效 token → 返回 `QuotaError.credentialsExpired`，文案「Claude 凭据已过期，请打开 Claude Code（或在终端运行 `claude`）刷新登录后再回来」。

#### 为什么不自己刷新

Claude 的 OAuth `refresh_token` 是 *一次性* 的：刷新即轮换，旧值立即作废，并且服务端带重用检测。同一个 `client_id` 下不存在「两份同时有效的 refresh_token」——cc-bar 每成功刷新一次，Claude Code CLI / Desktop 内存里那份就立刻变成废票，它们下次刷新拿到 `invalid_grant`，整条 token family 被撤销，**用户被迫重新登录**。

这不是靠「小心一点」能消除的：compare-and-swap 之类的写前比对保护的是磁盘状态，保护不了另一个进程内存里的副本。

关键权衡是收益侧：**cc-bar 需要刷新的时刻，恰好是数据不会变的时刻**。access_token 过期意味着用户已经很久没用 Claude Code，额度本来就没消耗，刷新换来的「新鲜数据」和快照里的旧数据是同一份。为一个不变的数字赌上用户主力工具的登录态，不划算。

同类工具的选择佐证了这一点：OpenChamber 与 cc-switch 对 Claude 完全只读（OpenChamber 的 quota 文档把理由写进了注释）；CodexBar 会刷新但只写自己的缓存条目，从不回写 `Claude Code-credentials`，且 0.47.0 起一度彻底停止读取该条目，原因是 Claude Code 每次刷新都会重写它的 ACL。

#### 过期后的降级链路

1. **保留快照**：`markClaudeFailure` 不清空 `claudeQuota`，上一次的额度条继续展示，只是标记错误。
2. **本地用量不受影响**：`Core/Usage/` 的 JSONL 统计不碰凭据，今日 / 本周 token 数、费用、模型分布照常工作。
3. **CLI 兜底取数**：用户手动刷新（`reason == .userInitiated`）且错误是 `credentialsExpired` 时，走 `ClaudeCLIFallbackQuotaClient`。`claude` CLI 用自己的会话身份，刷新对它是安全的，顺带把凭据刷新了，下一轮 cc-bar 重读就能直接采用。

#### 仍保留的两项协作机制

- **进程内去重**：`Coordinator` actor 合并菜单栏 / 悬浮窗 / Popover 几乎同时触发的重读——keychain 读要过一次 ACL，不便宜。
- **礼让窗口后重读**：存储在最近 `politeMtimeWindow=10s` 内被改过，认为 Claude Code 正在刷新的半途，sleep `adoptDelay=1s` 再读一次。两个源都支持：文件源看 mtime，keychain 源看条目属性里的 `mdat`（`security find-generic-password` 不带 `-w` 读属性不碰密文，不会触发钥匙串授权弹窗）。

> 删除的实现：`performNetworkRefresh` / `writeBackToFile` / `writeBackToKeychain` / `invalid_grant` 软恢复 / `ClaudeDelegatedRefresh`（PTY 唤起 `claude` CLI 代刷）。`QuotaError.tokenRevoked` 随之改名为 `credentialsExpired`，语义从「服务端拒绝了 refresh_token」变为「本地凭据已过期且我们不去刷」。
>
> 连带影响：`Helpers/CCBarClaudeWatchdog` 原本只为委托刷新做 TCC 隔离，现已无调用方；其 Embed 构建阶段仍保留在工程里，待单独清理。

## 6. 额度查询

### 6.1 接口

| 服务 | 请求 | 关键 Header |
|---|---|---|
| Codex | `GET https://chatgpt.com/backend-api/wham/usage` | `Authorization: Bearer …`、`ChatGPT-Account-Id`、`User-Agent: codex-cli` |
| Claude | `GET https://api.anthropic.com/api/oauth/usage` | `Authorization: Bearer …`、`anthropic-beta: oauth-2025-04-20`、`User-Agent: claude-code/2.1.0` |
| Antigravity | `POST https://127.0.0.1:<port>/exa.language_server_pb.LanguageServerService/RetrieveUserQuotaSummary` | `X-Codeium-Csrf-Token`、`Connect-Protocol-Version: 1` |

三者响应统一映射为 `QuotaSnapshot { primaryLimit, secondaryLimit, modelLimits, ... }`，每条 `QuotaLimit` 带 `fiveHour / weekly / modelWeekly / unknown` 语义。Codex 根据 `limit_window_seconds` 识别 5H 与 WK，并保留服务端主次顺序；Claude 合并旧的 `five_hour` / `seven_day` 与新 `limits` 数组，Fable 等 `weekly_scoped` 项进入 `modelLimits`。Antigravity 映射到相同主次模型，Gemini 仍走独立 GM/GW 字段。

#### Antigravity 本地探测

- `ps -ax -o pid=,command=` 只匹配官方 Antigravity App / IDE 的 `language_server`，CSRF token 仅保存在当前请求内存。
- 单轮刷新先生成一次 `Discovery`，availability 判断与后续 fetch 复用同一份进程列表，不重复执行 `ps`；不跨轮缓存 PID / CSRF token。
- `lsof -nP -iTCP -sTCP:LISTEN -a -p <pid>` 获取 loopback 端口；URL 始终由代码固定为 `127.0.0.1`。
- 自签名 TLS 只对 `127.0.0.1` 放行。App 的完整 quota summary 优先；失败后用 `GetUserStatus` 聚合 Claude / GPT 和 Gemini 模型配置作为 5H 兜底，再尝试 IDE 进程。
- 不读取 Google OAuth 文件、不启动 `agy`、不写 Antigravity 状态。内部协议升级导致失败时保留缓存。

### 6.2 调用策略

- 启动只读 `quota-cache.json` 灌进 AppState，**不**立刻打网络。
- 周期循环按设置间隔触发（额度默认 2 分钟，可设 1 / 2 / 3 / 5 / 10 分钟；代码层保留对 nil / 0 的兜底，设置 UI 无「关闭」入口）；任意一家上次成功 < 60s 时跳过。
- 收到 429 后该服务进入 10 分钟退避，期间所有触发短路。
- 手动刷新绕过 60s 节流，但仍遵守 429 退避。
- 401 / 403 不会自动停止循环（保持简单），但错误会显示在 Popover。
- 网络、本地服务或解析失败均保留旧快照，错误写入 `lastError`，下一 tick 重试。

### 6.3 Claude CLI 兜底

`ClaudeCLIFallbackQuotaClient` 只由 `refreshNow`（`reason == .userInitiated`）触发，且自身有 10 分钟独立冷却。两种进入条件：

- **API 取数失败** 且 `claudeQuota == nil`（手上一份快照都没有，需要救急）；
- **凭据已过期**（`QuotaError.credentialsExpired`）——cc-bar 不自己刷新，改由 CLI 用它自己的会话身份取数，顺带完成刷新。

行为细节：

- 候选可执行：`/opt/homebrew/bin/claude` → `/usr/local/bin/claude` → `/usr/bin/claude` → `env claude`。
- 用 `/usr/bin/script -q /dev/null <claude>` 包一层伪 PTY 拿到 ANSI 输出；失败再裸跑一次直接执行。
- 通过 stdin 写入 `/usage\n\n/status\n/exit\n` 驱动 CLI。
- 输出 strip ANSI，按 `Current session` / `Current week (all models)` / `Current week (Sonnet only)` / `Current week (Opus)` 标签抓百分比与 `Resets …` 文本。
- 错误关键词识别：`rate_limit_error` / `authentication_error` / `failed to load usage data`，转成对应 `QuotaError`。

CLI 兜底拿到的 snapshot 用 `QuotaSnapshotSource.cliFallback` 标记，仅用于救急展示。

### 6.4 持久化

`QuotaCache` 写 `~/Library/Application Support/CCBar/quota-cache.json`。v3 用 `providers[QuotaApp]` 保存语义化主次额度；读取 v2 快照时按窗口长度重新归类 Codex，旧 Claude Opus/Sonnet 转为模型专项额度，读取 v1 时继续迁移顶层 `codex` / `claude` 字段。

三个额度文件的写入统一走 `QuotaPersistenceCoordinator`（批次 C）：刷新 / bootstrap / 设置操作只更新内存并标脏（`QuotaFile` 集合），末尾构造不可变 snapshot 提交；coordinator 在 utility 任务里编码 + 原子写，同一文件一轮最多一次，串行提交 + pending 合并防止旧写入覆盖新版本。每次 flush 由 AppState 在 MainActor 上分配单调递增 `sequence`，coordinator 丢弃序列号不高于已写入的提交——`Task.detached` 的执行顺序无语言保证，序列号用于裁决乱序到达的过期快照。写盘失败只记日志，不回滚内存快照与 UI，下轮成功刷新会重新生成完整 payload 覆盖。周期边界滚动触发的受限重建仍按内存中的最新 `quotaCycles` 判断，不等写盘完成。

`QuotaHistoryStore` 写 `~/Library/Application Support/CCBar/quota-history-today.json`，只保存本地当天数据：

- `lastSamples`：每个账号最近一次成功采样的主要额度、窗口类型与剩余整数百分比。主额度类型改变时清理该账号当天旧基准和事件，避免跨窗口产生虚假涨跌；历史格式 v2 不迁移无法判型的 v1 当天记录。
- `events`：只有同一种主要额度的剩余整数百分比发生变化时才新增事件，字段包含账号 key、应用、账号类型、额度 ID/类型、采样时间、变动前 / 后剩余、delta 和重置时间。
- 启动和每次写入都会按本地 `Calendar.current.startOfDay` 清理非当天数据。
- Codex 主账号、Claude 主账号、每个导入 Codex 账号分别使用独立 key；镜像主 Codex 的导入账号只在主账号来源为 API 成功快照时记录。

### 6.5 服务状态（`ServiceStatusClient`）

OpenAI / Anthropic 各自的 Statuspage.io 公开接口,无需鉴权,用于在 Popover 中显示一个状态圆点：

| 服务 | 端点 |
|---|---|
| OpenAI | `https://status.openai.com/api/v2/status.json` |
| Anthropic | `https://status.claude.com/api/v2/status.json` |

响应中 `status.indicator` 取值 `none / minor / major / critical / maintenance`，未识别值归并为 `unknown`。`ServiceStatusClient.fetch` 解析为 `ServiceStatus { indicator, description, updatedAt, fetchedAt }`，10s 超时。

调用策略：

- `AppState.refreshServiceStatus()` 并发拉两家，单边失败不影响另一边；网络/解析失败保留上一份快照，不清空。
- 由 `Scheduler` 固定 5 分钟一次驱动；启动后立即拉一次；`refreshNow()` 也会顺带刷新。
- 仅做展示，不缓存到磁盘。

## 7. 本地 JSONL 扫描

`JSONLDirectoryEnumerator` 在递归枚举时一次取得 URL、mtime 与 size，Claude / Codex / Pi Scanner 复用这份 descriptor，不再逐文件二次查询属性。Codex 仍保留最多 4 路的变化文件并发解析，但未变化文件在创建 Task 前即被过滤，只用已有 `ScanFileState` 补会话 seed；扫描目录、存活文件判定、archive 去重、watermark 与统计口径不变。

### 7.1 Claude（`ClaudeJSONLScanner`）

- 入口路径 `~/.claude/projects`，遍历所有 `.jsonl`。
- 每条 `type=assistant` 行解析 `message.id` / `message.model` / `message.usage`（`input_tokens` 不含 cache_read）/ `stop_reason`。缓存写入 Tokens 对外仍使用 `cache_creation_input_tokens` 合计；计价时额外拆出 `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`。明细缺失时合计全部按 5m，明细与合计不一致时保留合计、1h 不超过合计、剩余按 5m。
- 本批次内按 `message.id` 取唯一，优先选 `stop_reason != nil` 或更高 output_tokens 的一条；最后与全局 `seen` 集合比对，避免 sidechain / subagent 文件中重复计数。
- 每条记录同时提取 `sessionId` / `cwd` / `gitBranch`；相同 `sessionId` 的主文件与 `subagents/` 文件合并为一个对话，档案标记是否包含子任务。
- 标题优先从 `~/.claude/history.jsonl` 按 sessionId 关联；未命中时取主会话第一条非注入 user 文本并清洗为最多 80 字摘要。
- 项目先收集同一 session 的全部 cwd 候选，再按 history project、唯一 Git 根目录、非 sidechain cwd、顶层项目容器匹配的顺序解析；无法可靠消除多个项目冲突时归为“无明确项目”，不依赖文件枚举顺序。
- 全局 seen 列表持久化在 `scan-state.json`，上限 20000，超出截尾。
- 流式 assistant 行只有在 `stop_reason != nil` 时才代表一次完整调用；半成品不入账，也不写入 seen，等待后续完整行由下一次增量扫描接收。永远没有结束行的中断请求不统计。

### 7.2 Codex（`CodexJSONLScanner`）

- 入口路径 `~/.codex/sessions` + `~/.codex/archived_sessions`。
- rollout 用文件名 / `session_meta.id` 的稳定 UUID 作为扫描状态 key；文件移入 `archived_sessions` 后继续沿用原 offset，避免重扫叠加。
- 标题优先从 `~/.codex/session_index.jsonl` 关联真实 thread name，未命中时取首条 `user_message` 摘要。
- `session_meta.cwd` 经标准化、符号链接解析和 Git 根目录识别后形成项目身份；已不存在路径仍保留为历史项目。
- `turn_context` 行更新当前模型（写入 `ScanFileState.lastModel`）。
- `thread_settings_applied.thread_settings.service_tier` 更新当前速度档位：`priority` / `fast` → Fast，`default` → Standard，其他值 → Unknown；写入 `ScanFileState.lastServiceTier`，增量续扫继承该状态。
- `event_msg` 且 `payload.type == "token_count"` 行，从 `payload.info.last_token_usage` 直接累计（不是累计 delta），`info == nil` 跳过。
- 每条 `token_count` 同时对 `total_token_usage` 的稳定字段生成签名并写入 `ScanFileState.lastCodexTotalUsageSignature`；设置切换后若累计签名没有变化，说明只是回显上一请求，跳过而不把它错归到新档位。
- Codex 的 `input_tokens` 含 cache_read；若 `last_token_usage.cache_write_tokens`（或 `input_tokens_details` / `prompt_tokens_details` / `token_details` 内同名字段）存在，`billable_input = input_tokens − cached_input_tokens − cache_write_tokens`。当前本地日志缺该字段时按 0，不推测缓存写入。

### 7.3 Pi（`PiJSONLScanner`）

- 入口路径 `~/.pi/agent/sessions/**/*.jsonl`（按工作目录分子目录，递归枚举）。
- pi 会话文件是 append-only JSONL，assistant 消息自带 `message.usage`（`input` / `output` / `cacheRead` / `cacheWrite` / `totalTokens`）与可选的 `message.cost`（USD 费用四类 + `total`）；`cost.total > 0` 时日志价格优先，缺失或为 0 且有 Token 时由统一 Pricing 按在线目录 → 本地价格表补算，仍无价才让 `costUSD` 为 nil。缺价条目会进入 `hasUnpricedUsage` 路径并触发远端价格刷新。
- 模型标签为 `provider/model`（如 `deepseek/deepseek-v4-flash`），避免不同 provider 模型重名；速度档位恒为 Standard（pi 无档位概念）。
- Pi 的四项日志费用与 `total` 只有 JSON 浮点尾差时，保留官方分项并把差额对齐到总价；明显不一致的分项不作为可靠构成。
- 解析 `type=message` 的 assistant 消息计入用量；`type=compaction` / `type=branch_summary` 带 `usage` 时也计入（对齐 pi `/session` 的 token/cost 合计口径，模型标签沿用文件内最近一条 assistant 的）；toolResult 嵌套 usage、label、model_change 等不参与。
- 会话标题取会话内首条 user 消息文本（清洗为最多 80 字）；项目身份由 `type=session` 的 `cwd` 经 `ConversationProjectResolver` 解析。
- 增量沿用 mtime + byte offset；跨文件按 `entryID@ISO timestamp` 全局去重（覆盖 `/fork` `/clone` 复制旧行到新文件导致的重复计费），全局 seen 上限 20000 截尾（同 Claude）。

### 7.4 OpenCode（`OpencodeScanner`）

- 入口 `~/.local/share/opencode/opencode.db`（OpenCode Desktop / CLI 共用同一 SQLite 库）；只读打开（`SQLITE_OPEN_READONLY`），与 OpenCode 运行中的写入通过 WAL 并发安全。库缺失 / 打开失败 / 表结构不符时本轮 no-op、保留原 watermark，不阻塞其他服务扫描。
- 解析 `message` 表每行 `data` JSON：user 消息带嵌套 `model{providerID, modelID, variant}`，assistant 消息自身带顶层 `providerID` / `modelID`；模型标签格式 `providerID/modelID`（对齐 Pi），variant 不拼入。增量扫描只追加 assistant 时模型标签可能丢失，回退到会话内最近 user 消息继承的模型兜底。
- assistant 消息自带 `cost`（USD）与 `tokens{input, output, reasoning, cache{read, write}}`；reasoning 并入 output（对齐 Claude / Codex 的 output 含 thinking 口径）。`total <= 0` 且无 cost（或 cost 为 0）的消息（工具调用收尾等）不计入。
- 费用：有效官方 `cost > 0` 时总额直接采用，价格链只用于估算四项费用占比并按官方总额缩放，不会覆盖官方总费用；缺失或为 0 且有 Token 时调用统一 `Pricing.resolveCostBreakdown`，按在线目录 → 本地价格表补算。最终 `UsageEntry.costUSD` 与 `costBreakdown.total` 始终一致，本地与远端都无价时按 `$0` 展示。`Pricing.normalize` 对 `opencode-go/` 前缀剥除，与本地表 / 远端目录对齐。
- 会话信息：`session` 表提供 title / directory，`workspace` 表提供 branch；空标题用该会话首条 text part 兜底。项目身份由 directory 经 `ConversationProjectResolver` 解析。速度档位恒为 Standard（无档位概念）。
- 增量：watermark 为 `max(message.time_created)`（Unix 毫秒），查询 `>= watermark` 并按 `message.id` 全局去重兜底 compaction / 时间戳回跳，seen 上限 20000 截尾；被删除的会话不回扫（与 JSONL append-only 假设一致）。
- **无订阅额度**：定位与 Pi 一致——不进入额度轮询、Popover 额度区、菜单栏、悬浮窗与 Timeline；仅在主窗口用量统计与对话页展示（`opencodeTodayCost` 供 Popover 今日花费合计使用）。

### 7.5 增量与持久化（`ScanCache`）

- 每个文件维护 `ScanFileState { mtime, offset, lastModel?, lastServiceTier?, lastCodexTotalUsageSignature?, conversationID?, conversationCwd?, conversationGitBranch?, conversationIsSidechain?, fallbackTitle? }`；Claude 按路径保存轻量会话摘要，让未变化文件也能重新判断项目可用状态，Codex 按稳定 conversationID 维护。Codex 文件截断时 offset、模型、速度和累计签名一起重置。
- 调度逻辑：`mtime == prev && offset == size` → 跳过；`offset > size` → 文件被截断，归零重扫（去重靠 seen 集合）；否则从 `offset` 处续读到末尾。
- **时间戳解析走手写快路径**：`JSONLTimestamp.parse` 先按 UTF-8 字节解析 `YYYY-MM-DDTHH:MM:SS[.fff…][Z|±HH[:]MM]`，形状不符再回退到复用的 `ISO8601DateFormatter`。除实例创建外，`date(from:)` 单次调用本身也很贵（内部走 CFDateFormatter 的通用格式状态机），实测占整轮日志扫描 CPU 的一半以上。快路径同样要求必须带时区、且必须完整消费整个字符串，与 `.withInternetDateTime` 的接受范围严格一致，不放宽也不收窄，避免把原本解析失败的行变成有效条目。
- 已不存在的文件 watermark 在每次扫描末尾清理。
- **scan-state 常驻内存**：`scan-state.json` 只在冷启动且日聚合、对话两份主 rollup 恢复成功后的首轮扫描中读盘解码；周期 rollup 若存在也必须同代、同价格指纹，否则仅丢弃周期缓存并重建。此后每轮复用 `UsageService` 内存中上一轮已提交的 `ScanState`，内存路径执行与读盘路径相同的 generationID / 价格指纹校验（价格目录 commitPending 后指纹变化照旧触发全量重建）；持久化失败时清空内存副本并标记失效，下轮直接全量重建。
- **标题索引缓存**：`ConversationTitleIndex` 对 `~/.claude/history.jsonl` / `~/.codex/session_index.jsonl` 按 (mtime, size) 缓存解析结果，索引文件未变化的轮次不重读不重解析。
- 四份扫描缓存（scan-state / usage-rollup / conversation-rollup / cycle-usage-rollup）均为机器读文件，JSON 编码不使用 sortedKeys，省掉每轮写盘的全量键排序。
- 顶层结构 `ScanState { version, generationID, pricingFingerprint, claude, codex, claudeSeenMessageIds, pi, piSeenEntryIds, opencodeLastMessageTime, opencodeSeenMessageIds }`，版本号 v12（v10 新增 pi 扫描 watermark，v11 新增 opencode watermark，v12 统一 Pi/OpenCode 费用解析口径，各自触发一次全量重建把对应历史数据扫入）。`UsageRollupPayload` 为 v9，`ConversationRollupPayload` 为 v6；三者共享同一 `generationID`，任一缺失或错代都触发全量重扫，避免部分写入后让 watermark 越过尚未持久化的聚合数据。
- **失效条件有三类**：`version` 管结构变更，`pricingFingerprint`（`Pricing.fingerprint(knownUsage:)`，价格内容的 SHA-256）管价格变更，`generationID` 管四份扫描相关缓存的提交一致性。任一不满足即整份丢弃；`UsageService` 会先清空内存聚合器，再全量重扫重算历史桶，绝不把全量结果叠加到旧桶。改本地价格表、或远端价格目录里已用过的 app/model/speed 调价后无需手动 bump 版本号——指纹自动失效，避免「改了价却忘了重算」导致历史 cost 不一致。`knownUsage` 由当前桶的 `(app, model, speed)` 推导；三份 rollup cache 都能用 payload 自带 buckets 自包含校验。详见 §7.6。

### 7.5 聚合（`UsageAggregator`）

- `@Observable @MainActor`，内存 `[BucketKey: UsageBucket]`，BucketKey = (day, app, model, speed)。
- `ingest(entries)` 累加 token 与 cost；`snapshot()` 返回数组用于落盘；`todayCost(for:)` / `totals(app:from:to:)` 给 UI 用。
- 由于是 `@Observable`，Popover 和统计 tab 在 body 读 `aggregator.totals(...)` 时自动建立依赖，新扫描完写回 buckets 后 UI 自动刷新。
- **Token 展示口径**：`UsageTotals.inputWithCacheTokens = input + cache_read + cache_creation`，`totalTokens = inputWithCacheTokens + output`。Stats 页的"总令牌 / By service tokens / By model 入"统一使用此口径，与 cc-switch / ccusage 对齐；其中 Claude 的 `input_tokens` 本身不含 cache_read，Codex 的 `inputTokens` 在解析时已扣过 `cached_input_tokens`，因此三项相加不会重叠。
- `UsageSpeedBreakdown` 分别汇总 Standard / Fast / Unknown。原始 Tokens 不乘倍率；只有 Fast 桶另算 `fastBillingEquivalentTokens`。未收录倍率时等效 Tokens 按 0；聚合范围只要混入任一未收录倍率的 Fast 模型，倍率统一显示 `—`，不能只显示已知模型的倍率而让它与总 Fast Tokens 不一致。未收录档位费率时金额按 `$0` 展示。

### 7.5a 对话聚合（`ConversationAggregator`）

- 与日聚合并行维护 `ConversationInfo` 和 `(conversationKey, day, model, speed)` 桶；列表可按时间范围汇总，右侧详情聚合对话完整生命周期。
- 档案只保存 ID、最多 80 字标题摘要、项目 key / 名称 / 规范路径 / 状态 / 来源、分支、源文件路径和起止时间，不保存完整消息正文。
- `ConversationProjectResolver` 对扫描中的唯一原始路径做 memoized 文件系统检查：存在时解析 symlink 和最近 Git 根目录；`/` / 用户主目录归为无明确项目，CCBar wakeup / probe 归为系统任务，已删除路径标记 unavailable。同名路径不合并。
- `ConversationQueryRequest / ConversationQueryResult` 把 app、projectKey、时间、搜索与排序合并为一次查询：单次遍历同时生成对话行、项目选项、项目 key 和重名集合。聚合器以 `revision` 标记 load / ingest 后的数据版本，并 memoize 最近一次查询；SwiftUI 重绘复用快照，不重复聚合。
- 详情按 `(conversationKey, revision)` 缓存，只有切换对话或扫描数据变化时重新聚合完整生命周期；seed 的标题、项目、路径等字段与现有档案完全一致时不递增 revision。无 Token 桶的 seed 不进入持久化档案，避免产生无效起止时间。`isEmpty` 直接读取桶状态，不通过 `snapshot()` 复制全量数据。秒级“上次更新”文字由独立视图刷新，不使列表查询失效。
- `ConversationUsageBucket` 同时保存速度档位、请求数、四项 Token、四项成本及内部缺价标记；查询层生成 Standard / Fast / Unknown 明细以及 standard / fast / mixed / unknown 状态。缺价部分金额按 0 汇总，UI 只展示最终数值，不追加缺价文案。
- `ConversationRollupCache` 写入 Application Support 下的 `conversation-rollup.json`，价格指纹变化时与日聚合一起丢弃并全量重算。

### 7.6 价格（`Pricing` + `PricingCatalogStore`）

**统一解析**：扫描器统一调用 `Pricing.resolveCostBreakdown`。Pi / OpenCode 日志中的有效总价（`cost > 0`）直接采用，不会被价格表改写；Pi 保留浮点尾差范围内的官方分项，OpenCode 则用价格表估算分项占比并按官方总价缩放。日志价格缺失或为 0 且有 Token 时，再按 Standard API 价格链查在线目录 → 本地价格表。最终 `UsageEntry.costUSD` 与 `costBreakdown.total` 始终相同，统计页和对话页只消费这个最终结果。Codex / Claude 既有的 A/B 价格来源规则保持不变。

- **A 类**（`Pricing.localOverrideKeys` = `contextPriceTiers.keys ∪ timedOverrides.keys ∪ fixedLocalOverrideKeys`）：受本地特殊规则管辖，远端价格目录**零参与**。
  - GPT-5.6 Standard 使用 OpenAI Standard API 官方费率，覆盖 `gpt-5.6`（Sol 别名）、Sol、Terra、Luna；`gpt-5.6-pro` 不存在，Pro 为 reasoning.mode。每个模型用 `ContextPriceTiers { longContextThreshold, shortContext, longContext }` 表达两个完整费率，完整输入 `>272_000` 时输入、缓存读、缓存写和输出均切到长上下文价。未实现 Batch / Flex 费率选择。
  - GPT-5.5 Standard 同样在完整输入 `>272_000` 时切换长上下文价：输入 `$10`、缓存读取 `$1`、输出 `$45` / MTok；`<=272_000` 使用 `$5 / $0.50 / $30`。GPT-5.5 Pro 是独立模型，固定使用输入 `$30`、缓存读取 `$30`、输出 `$180` / MTok；官方没有缓存折扣，因此它列入 `fixedLocalOverrideKeys`，不接受远端目录覆盖。
  - `timedOverrides`：按历史日期分段生效价，取用量记录发生时间对应的分段。当前无模型使用（Claude Sonnet 5 原定 2026-09-01 换新价 $3/$15 已取消，官方确认 $2/$10 为固定标准价，改列 `fixedLocalOverrideKeys`）。
  - GPT-5.6 的 `cache_write_tokens` 按独立 cache-write 费率计入；Codex 当前本地日志未记录该字段，因此缺失时按 0，展示的是基于本地日志可得字段的官方 API 价格折算估算，而非账单对账。
- **B 类**（其余扁平价模型）：`PricingCatalogStore.shared.rate(for:app:speed:)` 的 Standard 价格优先（LiteLLM 优先于 models.dev），命中不到才回落内置 `table`；两者都没有时 `Pricing.cost()` 内部返回 `nil`，聚合与 UI 按 `$0` 处理。
  - **已知边界**：远端只提供「当前单一价」，没有历史分段，B 类模型一律用当前合并价重算全部历史。如果某个 B 类模型实际曾经调过价、需要精确历史计价，做法是把它升级为 A 类、手工加进 `timedOverrides`（发版维护）。

**`PricingCatalogStore`**（`Core/Pricing/`）：内存快照 + v2 磁盘缓存 + 后台刷新，用锁（`OSAllocatedUnfairLock`）保护而非 `actor`，因为 `rate(for:app:speed:)` 必须保持同步调用（两个 Scanner 同步调用 `Pricing.cost()`）。v1 缓存启动时迁移为 Standard rates，Fast rates 初始为空；迁移会清除旧 ETag / 刷新时间以强制一次完整拉取，既保留离线数据，也避免 304 让 Fast 永久空缺。

- 远端源：LiteLLM `model_prices_and_context_window.json`、models.dev `api.json`，各自独立 ETag / 24h 刷新间隔 / 失败 30min 退避。
- 匹配规则：LiteLLM 只取不含 `/` 的裸键，且 `litellm_provider ∈ {anthropic, openai, deepseek}`；Standard 解析基础字段，Fast 仅把 OpenAI `*_priority` 字段映射为 Codex Fast，不混淆 Anthropic Priority Tier。models.dev 只取 `anthropic`/`openai`/`deepseek` 三个官方 provider 下的 `models`，Standard 解析 `cost`，Fast 解析 `experimental.modes.fast.cost` 并按 provider 分入 Codex/Claude 两张表；转售商同名条目继续过滤。两侧都对 key 跑 `Pricing.normalize()`，裸名优先，日期后缀变体仅在裸名缺失时兜底填坑。
- 刷新触发有三条：App 启动和每次 `scanNow()` 开头用 `refreshIfNeeded()` 做 24h 常规检查；扫描结束发现 Standard/Fast 缺价时调用 `refreshForMissing()` 绕过 24h，同一 app/model/speed 的尝试时间持久化且 30 分钟内不重复；设置页“价格目录”按钮调用 `forceRefresh()` 手动绕过 24h。Unknown 档位、已有可靠价格但请求级不支持的场景，以及明确不计价的 `codex-auto-review` 不触发缺价刷新。
- 快照一致性：刷新结果先进入 pending，只在扫描开始或一批扫描结束后的安全边界原子提交为 active；一整批扫描、缓存校验和最终 fingerprint 都只读取同一份 active 价格表。缺价刷新拿到新价后自动排队下一轮，指纹变化会触发完整历史重算。
- 保护链：网络失败 / 非 2xx / JSON 解析失败 / 解析结果为空、或相较已有 20 条以上缓存异常缩水超过一半时，一律保留旧快照并进入 30 分钟退避，不覆盖已有好缓存。可疑内容会清除该源 ETag，确保下次完整拉取重新验证；磁盘缓存 `pricing-catalog.json` 损坏或不存在时回退空 payload（= 纯内置表兜底，不影响现有计价能力）。
- 只请求两个公开 JSON URL，不上传任何本地用量 / 账号信息。

**通用**：

- **Fast 分流**：`Pricing.costBreakdown(app:model:speed:...)` 先按档位选择价格。Standard 继续走 A/B 价格链；Unknown 内部返回 nil、金额按 0；Fast 只接受带明确档位语义的在线 rates，models.dev 官方 provider 优先、LiteLLM OpenAI Priority 兜底，命中不到再回落 `codexFastPrices` / `claudeFastPrices`。完整输入 `>272_000` 的 Codex Fast 仍按 0；GPT-5.5 因上游曾存在旧 Priority 价而使用已审计本地固定覆盖，Opus 4.6/4.7 使用固定本地历史价。远端 Fast 条目消失时不删除 last-known rate，避免历史日志突然归零。`billingEquivalentMultiplier` 中 Codex ChatGPT credit 倍率仍只走本地表；Claude 仅在 Standard/Fast 四项非零比例完全一致时允许在线推导。
- **Claude 缓存 TTL**：`Pricing.costBreakdown` 的 `cacheCreation` 表示普通/5m 写入，继续使用模型表中的 1.25× cache-write 费率；新增 `cacheCreation1h` 使用当前 Standard / Fast 基础输入价的 2×，两部分只在 `CostBreakdown.cacheCreation` 汇总，不增加 UI 字段。1h 倍率规则加入价格指纹；Pi/OpenCode 费用口径改变则通过 v12/v9/v6 结构版本自动全量重扫回算历史费用。
- Fast 规则来源（2026-07-16 口径）：[Codex Fast mode](https://learn.chatgpt.com/docs/agent-configuration/speed#fast-mode)、[OpenAI Priority Processing](https://openai.com/api-priority-processing/)、[Claude Fast mode](https://platform.claude.com/docs/en/build-with-claude/fast-mode)。这些规则可能调价，因此价格和倍率都纳入本地指纹。

- 归一化（`Pricing.normalize`）：剥 `openai-codex/`、`openai/`、`anthropic/`、`deepseek/`、`opencode-go/` 前缀；Vertex 风格 `name@YYYYMMDD` 截断 `@` 前；Anthropic 风格 `-YYYY-MM-DD` 或 `-YYYYMMDD` 后缀剥掉；最后 `lowercased()`；远端目录 key 归一化复用同一套规则。
- 金额用 `Decimal`（`Foundation.Decimal`），单位 USD / 百万 token。`Pricing.cost()` 返回 `Decimal?`：`nil` 表示没有可靠费率，`UsageAggregator.ingest` 聚合时按 0 处理；内部缺价标记继续保留给诊断使用，但 UI 不展示。
- `Pricing.costBreakdown()` 与 `cost()` 使用同一费率选择，返回输入 / 输出 / 缓存读取 / 缓存写入四项 Decimal；返回 nil 时四项费用在 UI 中均按 0 展示。
- `Pricing.fingerprint(knownUsage:)`：哈希内容 = 本地 `table` + `contextPriceTiers` + `timedOverrides` + Standard/Fast 固定本地覆盖 + Fast 本地价格/倍率 + Claude 缓存 TTL 倍率 + 当前用量中实际出现过且远端命中的 app/model/speed 合并价。只算已使用子集，远端新增无关模型不触发重扫；相关 Standard 或 Fast 价格变化会让四份扫描相关缓存失效并全量重算。

### 7.7 协调（`UsageService`）

- `bootstrap` 同时读取 `usage-rollup.json`、`conversation-rollup.json` 与 `cycle-usage-rollup.json`，立即恢复现有统计、对话列表和周期统计。三个 rollup 的磁盘读取 + JSON 解码（conversation-rollup 实测可达数 MB）放在后台线程执行，不阻塞启动主线程；周期 rollup 中的 cycleID 必须仍存在于清理后的周期记录，否则只丢弃周期 rollup 并触发重建，避免合并 resetAt 漂移残片后遗漏其本机用量。周期 rollup v4 修复受限重建重复累加；载入 v3 或更旧派生数据时丢弃旧 rollup 并自动完整重建一次，`quota-cycle-history.json` 的周期边界与账号段不受影响。
- `scanNow()` 中 Claude / Codex / Pi / OpenCode 并行增量扫描，一批 entries 同时写入 `UsageAggregator`、`ConversationAggregator` 与符合主账号周期条件的 `CycleUsageAggregator`；只有对应聚合结果真实变化时才重新编码 rollup，watermark 变化时才写 scan-state，完全无变化的轮次不写盘。
- Claude / Codex 扫描结果会显式上报 JSONL 读取失败。根目录从未存在表示该 Provider 尚无本地会话，是可成功重建为空的正常状态；只有目录存在但无法打开、或 JSONL 实际读取失败才算失败。文件在枚举后、读取前被归档或清理时，`JSONLLineReader` 会复查路径并将其归为正常消失：不增加失败数、不显示警告，本轮保留旧 watermark；Codex 下轮可凭同一会话 ID 在 `archived_sessions` 从原 offset 续扫，避免归档后从 0 重复计入，真正删除的状态则由下轮 alive 集清理。常规增量扫描保留成功文件的结果，失败文件不推进 watermark，并写入 `lastError` 等待下轮重试；初始/受限周期重建按 Provider 隔离，失败侧保留原周期桶，成功侧仍可清桶重灌，避免 Claude 的问题阻塞 Codex（反之亦然）。`lastError` 会在统计页显示可见警告，并提供直达设置页“重新计算用量”的入口。
- 持久化先原子写 `usage-rollup.json`、`conversation-rollup.json` 与 `cycle-usage-rollup.json`，最后提交 `scan-state.json` watermark；四份文件共享 generationID。任一保存失败都会删除 scan-state、设置 `lastError` 并让下次扫描强制全量重建，不能把部分写入当成成功刷新。
- `QuotaCycleStore` 只记录功能启用后主账号 primary / secondary 中实际观察到的 `.weekly` 与 `.fiveHour`；不反推启用前周期，模型专项额度和导入 Codex 账号也不进入周期统计。采样**不按 `is_active` 过滤**：`is_active` 只表示「当前哪个限制在起约束作用」，非当前约束的窗口（如 5 小时未满时的 weekly）同样返回有效 percent / resets_at，过滤会导致周期记录停更、页面停留在旧值。精确 `(accountKey, limitID, resetsAt)` 与 60 秒内抖动优先命中原记录；若 resetAt 发生更大漂移，但同账号 / 同周期类型的旧记录仍有效且已用比例没有明显回落，也只在新旧边界相差不超过 30 分钟时继续更新原周期并保留最早起点，避免无变化的分钟级漂移产生伪周期，也避免低用量提前重置被串入旧周期。命中原记录后，`scheduledEndAt` / `endAt` 只在新旧边界相差 ≥5 秒（`scheduledEndJitterTolerance`）时才改写：服务端每次返回的 `resets_at` 都在抖动（实测 Claude 亚秒级、Codex 1~3 秒），若逐次写入，`cycleUsagePartition` 会把抖动当成周期边界滚动，使受限重建从「每天数次」退化成「每个额度刷新周期一次」，且让 `quota-cycle-history.json` 每轮刷新都被无谓重写。只有已用比例真实回落或旧周期到期才新建周期；新旧周期只有重叠超过 60 秒才会收口旧周期，秒级重叠视为同源边界抖动。相同 `resetsAt` 下的明显回落则在周期内新建 allowance segment，保留重置前后的独立基线。载入 v2～v4 数据时幂等删除秒级残片、合并重叠记录，并按相同回落规则接回相邻漂移片段；只有较 `scheduledEndAt` 提前截断超过 60 秒的相邻片段才是漂移合并候选。去重要求重叠**超过 60 秒**（`overlapDeduplicationMinimum`）才算重复记录：相邻的两个真实周期，边界分别由各自采样时刻的 `resets_at` 推出，两侧抖动叠加会让后一周期起点比前一周期终点早亚秒到数秒，这只是边界毛刺；真正的重复来自同一周期的 resetAt 漂移，重叠接近整个窗口（≥5 小时）。此处误判的代价不可逆——`merging` 只保留 base 的 `startAt` / `endAt`，被吞记录覆盖的整段周期历史会永久丢失且无法从日志重建。服务缺失窗口长度、只能按已知 5H / 7D 长度确定起点时边界为 inferred。
- 同一服务的主账号切换会持久化为半开区间账号时间段；精确请求先按时间段确定账号，再进入对应周期，保证全量重建不串号、环比不跨账号。Claude 主账号键使用规范化 email 的 SHA-256，不落盘明文邮箱；旧版常量键 `claude:primary` 无法还原真实账号，升级后一次性归入当前识别到的 Claude 账号，保留原 cycleID 以继续关联已有 rollup。邮箱缺失时暂退化到旧常量键，待身份可用时再迁移。
- `CycleUsageAggregator` 用请求 `timestamp` 按 `[startAt,endAt)` 同时归入对应周周期与 5H 周期，再按额度段半开区间归桶。首个账号时间段从 `QuotaCyclePayload.trackingStartedAt` 开始；周期重建即使读取空 watermark JSONL，也会排除该时间之前的请求，不读取日聚合残差或 Claude 补录数据。用满预估只使用当前额度段的本机用量和 `maximumUsedPercent - baselineUsedPercent`：观察变化与 Tokens 大于 0 即输出 Token 预估，观察变化与已知费用大于 0 即输出费用预估，`incomplete` 和部分未定价只影响标注；发生重置时用“此前额度段实际用量 + 当前额度段满额预估”，避免把累计费用除以清零后的比例。当前额度段 observed 为 0 时保留本机实际用量，但不生成用满预估或可信度；不能把首次采样的官方快照比例回退成观察增量。
- **周期用量重建分两条路径**：① 冷启动且 cycle rollup 无效（版本升级 / 价格指纹变化 / 首次启用）时，`rebuildCycleUsageIfNeeded()` 按待完成 Provider 全量重扫对应历史日志；v4 rollup 除全局 `initialRebuildCompletedAt` 外还持久化 `initialRebuildCompletedApps`。成功侧独立置位，失败侧保持待重试，因此下次启动只扫描失败侧，不会因一个永久不可读文件让健康 Provider 反复全量重扫；旧 v4 没有该字段时，全局完成时间非空会兼容视为 Codex / Claude 均已完成。② 周期窗口滚动 / 账号段变化时（`recordQuotaCycles` 检测到 partition 变化），`rebuildCycleUsageForRecentChanges()` 做**受限重建**。受限重建先用当前 watermark 跑一次常规增量扫描并正常提交，避免窗口重扫已灌入的新日志被下次增量扫描再计一次。重建基准窗口是最近 8 天，但扫描下限会向前扩展到受影响周期中最早的 `startAt`，保证清桶后灌回跨窗口周期的全部用量，不会逐日削减周期开头。Claude 和 Codex 均按文件 mtime 过滤（Codex 递归扫 `sessions` / `archived_sessions` 两个根目录，因此包含平铺归档和旧日期目录里近期续用的会话），且跳过标题索引构建。`CycleUsageAggregator.rebuildRange` 先清除受影响周期的旧桶，并且只允许扫描条目重新归入同一组周期；空集合直接 no-op，因此相同扫描结果重复执行保持幂等，窗口外历史桶不会被重复追加。受限重建与冷启动全量共用 `commitCycleAggregation` 收尾（聚合 → 落盘 rollup → 更新内存状态）；只有初始重建会更新 Provider 完成集合，受限重建不会把待重试侧误标完成。
- `CodexJSONLScanner` 文件间并行解析（`maxConcurrentFiles = 4` 路 TaskGroup，按原始顺序合并结果），全量重扫 / 强制重算是主要耗时场景（codex 历史日志可到 GB 级），多核并行显著缩短耗时；跨文件共享的 `cacheCreationKeys` 语义不变（批次内任意文件写过的会话统一补标到 seed）。claude / pi / opencode 保持串行（claude 有跨文件 message.id 去重，并行化风险高、收益低）。
- 扫描中再次调用 `scanNow()` 不并发启动第二批，而是登记一次 queued scan；当前批完成后自动补跑，避免刷新点击时恰好有日志追加而漏到下一周期。

### 7.8 个人历史用量补录（`ImportedUsageBackfill`）

- 起因：Claude Code 默认 30 天自动清理本地 `~/.claude/projects` jsonl，早于 cc-bar 扫描到就被删除的日期永久无法重新计算。`bootstrap()` 在常规 rollup 恢复之后，额外读取 `~/Library/Application Support/CCBar/imported-usage-claude-2026H1-gapfill.json`（若存在），按 `existingDays` 过滤掉 cc-bar 已有的日期后 `ingest` 进聚合器；文件不存在时是纯 no-op，不影响其他安装。
- 合并发生在两处，规则相同（按天去重）：`bootstrap()` 合并一次保证首轮扫描前即可展示；`runScan()` 每轮在扫描 entries ingest 之后、快照落盘之前再合并一次。后者是必需的——补录可能引入本地日志里不存在、但远端价格目录里有价的 app/model/speed，这些键进入 `knownUsage` 后会改变 pricingFingerprint；若只在 bootstrap 合并，缓存失效路径清空聚合器后落盘的 rollup / scan-state 指纹不含补录用量，下次启动指纹比对必然再次失效，形成「每次启动全量重建 + 补录被冲掉」的死循环。在 runScan 内合并后，落盘快照与指纹始终包含补录数据，指纹自洽、循环终止。
- 当前实现只认一个固定文件名，不是通用的多批次导入机制；后续如需支持其他数据源或多个批次，需要先扩展这里再动手补数据。
- 数据来源、过滤规则、如何用 AI 从其他工具（如 cc-switch）里生成同样格式的补录文件，见 [历史用量数据补录指南.md](历史用量数据补录指南.md)。

## 8. 调度（`Scheduler`）

`@MainActor`，持有 AppState 弱引用，三条独立 `Task` 循环：

- **额度循环**：`quotaInterval` 秒触发一次 `appState.refreshQuotas(reason: .periodic)`。设置项可选 `1 / 2 / 3 / 5 / 10` 分钟，默认 2 分钟；`Scheduler` 仍保留对 `nil` / 0 的兜底，不启动循环。
- **用量循环**：`usageInterval` 秒触发一次 `appState.usageService.scanNow()`。设置项可选 `1 / 2 / 3 / 5 / 10` 分钟，新安装默认 5 分钟；启动时仍立即扫描一次，用户手动刷新也会立即触发。已写入 UserDefaults 的旧选择不迁移、不覆盖。
- **服务状态循环**：固定 5 分钟触发一次 `appState.refreshServiceStatus()`，与额度/用量解耦（statuspage 变化慢，无需跟随用户的额度刷新间隔）。

`setQuotaInterval` / `setUsageInterval` 在间隔变化时取消旧 task 并按新参数重启，对应设置变更的实时生效。

## 13. 已知技术债 / 持续关注

- **Claude CLI 兜底依赖外部进程**：用户没装 CLI 时会失败，目前只在 API 失败且无缓存的手动刷新触发，影响面有限。
- **B 类模型历史精度**：远端价格目录（LiteLLM / models.dev）只提供「当前单一价」，没有历史分段，B 类模型的历史用量一律按当前合并价重算。若某个 B 类模型实际曾经调过价、需要精确历史计价，需升级为 A 类、手工加进 `Pricing.swift` 的 `timedOverrides`（发版维护）。A 类模型（GPT-5.6 / GPT-5.5 阶梯价、Claude Sonnet 5 固定价）不受此限，远端零参与。
- **特殊规则仍需手维护**：`contextPriceTiers` / `timedOverrides` / Fast 历史固定覆盖以及 Codex ChatGPT credit 倍率仍需同步 `Pricing.swift`；改表后由 `Pricing.fingerprint(knownUsage:)` 自动失效缓存触发重扫。其余 Standard/Fast 扁平价可由 `PricingCatalogStore` 后台补齐。
- **seen ID 上限 20000**：极端长时间使用 + 大量 sidechain 引用可能导致环形丢失；目前足以覆盖正常使用。
- **没有自动更新通道**：发布要手动出包；后续可接 Sparkle。

## 14. 导入账号（其他 Codex 账号）

用户可在设置页手动粘贴 `~/.codex/auth.json` 内容，为 cc-bar 添加任意多个 Codex 副账号（仅查看配额，不影响 CLI 的当前登录状态）。

### 14.1 设计原则

- **凭据与默认账号解耦**：默认账号始终来自实时读取 `~/.codex/auth.json`（cc-switch 切号也跟着变）；导入账号是独立副本，各自维护 token，绝不写回 `~/.codex/auth.json`。主 Codex 启用且导入账号与当前默认账号身份相同时，额度展示与刷新状态复用默认账号快照，不再读取导入 token 或重复请求官方接口；同时把当前默认账号 token 同步到该导入账号的 Keychain 副本，修复导入凭据长期未更新导致的后续刷新失败。主 Codex 关闭时不做镜像，可见导入账号使用自身 Keychain 凭据独立刷新。
- **允许重复（仅存储 / 管理界面）**：同一账号 ID 可以同时出现在默认槽和导入列表，语义不同（「当前 CLI 登录」vs「已导入的持久监控副本」）。存储层与设置页作为管理界面保留双份、不去重；刷新时镜像默认账号数据。**纯展示界面（Popover、统计页）则按身份去重**，同一账号只显示一次（见 §14.8）。
- **同 ID 覆盖**：再次粘贴相同账号时静默覆盖 token（保留 alias / visible 设置），避免悬空旧 token。
- **Team 账号区分用户**：账号身份用 `{chatgpt_account_id}:{chatgpt_user_id}` 复合键，同一 Team account 下不同 user 视为独立条目；缺失 `chatgpt_user_id` 时退化为单段 `chatgpt_account_id`（老数据兼容）。HTTP 请求里的 `ChatGPT-Account-Id` header 仍只取前半段。

### 14.2 存储

| 数据 | 位置 | 说明 |
|---|---|---|
| 元数据（id / alias / email / planType / visibleInPopover / addedAt） | `Application Support/CCBar/imported_codex_accounts.json` | 原子写，JSON version = 1。`id` 为 `{account_id}:{user_id}` 复合键 |
| Token 三件套（access / refresh / id） | macOS Keychain，`service = com.cc-bar.codex.imported`，`account = ImportedCodexAccount.id`（复合键） | SecItem 直接读写，不弹用户授权 |
| 额度快照缓存 | `quota-cache.json` 的 `importedCodex` 字段（`[String: QuotaCacheRecord]`） | 重启时立即显示上次数据 |

### 14.3 Token 续期回写隔离

`CodexTokenRefresher.ensureFreshAccessToken` 新增 `writeBack: WriteBack` 参数：
- `.codexAuthJSON`（默认）：续期后覆盖写回 `~/.codex/auth.json`，与现有行为一致。
- `.importedAccount(id:)`：续期后仅更新 Keychain 对应条目，不碰 `~/.codex/auth.json`。

### 14.4 刷新调度

`AppState.loadAllImportedCodexQuotas(reason:canMirrorPrimary:)` 在 `refreshQuotas` 中调用，对所有 `visibleInPopover = true` 的导入账号：
- 分批并发，每批最多 3 个同时 in-flight（chunked TaskGroup）。
- 每个账号独立维护 `QuotaRefreshState`（backoff / inFlight / lastSuccessAt），互不影响。
- 主 Codex 启用、且导入账号与当前默认 Codex 账号匹配时（优先 `{chatgpt_account_id}:{chatgpt_user_id}`，任一侧缺 user_id 时退回纯 account_id），直接镜像 `codexQuota / codexQuotaError / codexRefreshState`，不续期、不请求第二次 `wham/usage`；若默认账号有 `access_token`，先比较导入账号现有 token，只有 access / refresh / id 任一变化时才写 Keychain。主 Codex 关闭时跳过镜像，导入账号按独立账号链路刷新。

### 14.5 排序

- 列表顺序即 `imported_codex_accounts.json` 中 `accounts` 数组顺序,Popover「其他账号」按相同顺序展示。
- 设置页支持拖动排序:每行 `.draggable(account.id)` + `.dropDestination(for: String.self)`,放下后调 `AppState.reorderImportedCodexAccounts(orderedIds:)` 写回 `ImportedCodexStore.saveAll`,再触发 `reloadImportedCodexAccounts` 同步运行时。
- 新增的账号追加到列表末尾;`reorderImportedCodexAccounts` 对未在传入 ids 中的条目自动追加到末尾,避免丢失。

### 14.6 Paste 解析（ImportedCodexPaste）

支持三种粘贴形态：
1. **完整 auth.json**（`{OPENAI_API_KEY, tokens: {...}, ...}`）
2. **裸 tokens 子对象**（`{access_token, refresh_token, ...}`）
3. **personal access token**（`{"OPENAI_API_KEY": null, "personal_access_token": "at-..."}` 或裸 `{"personal_access_token": "..."}`）

形态 1/2 解析优先级：`tokens.account_id` → `access_token` JWT payload → `id_token` JWT payload。
email / planType 从 `id_token` 解，缺 id_token 时再从 `access_token` 的 JWT 里找。

形态 3（PAT）由 `ImportedCodexPaste.personalAccessToken(in:)` 识别（仅在无 OAuth tokens 时命中）。PAT 不透明、本地解不出 `account_id`，因此走独立路径：保存时由 `AppState.importCodexPersonalAccessToken(token:visibleInPopover:)` 联网发一次 `wham/usage` 验证令牌并拿回 `account_id` / `user_id` / `email` / `plan_type`，组出复合 id `{account_id}:{user_id}` 落库，并置 `ImportedCodexAccount.isPersonalAccessToken = true`。该字段为可空 Bool（兼容旧数据，nil 视为 false）；刷新时（`loadImportedCodexQuota`）PAT 账号跳过续期、直接用令牌、不带 `ChatGPT-Account-Id` header。

### 14.7 额外重置 credit（懒加载，主账号 + 导入账号）

`CodexResetCreditsClient.swift` 独立封装 `GET wham/rate-limit-reset-credits`，与 `wham/usage`（额度快照）完全解耦：不参与 `QuotaSnapshot`、不写入 `quota-cache.json`、不接入 `Scheduler` 定时刷新。

- 入口：设置页「账号」组的 Codex 主账号行、以及「其他 Codex 账号」每行都有一个 `gift` 图标按钮，点击展开/收起明细，仅在首次展开时发起一次请求，结果缓存在 View 的 `@State` 里（不持久化，关闭设置页 / 重新展开视图后失效需重新拉取）。
- 取数：
  - 导入账号：`AppState.fetchImportedCodexResetCredits(account:)`，token 处理与 `loadImportedCodexQuota` 一致（PAT 直接用令牌，OAuth 账号先 `CodexTokenRefresher.ensureFreshAccessToken(writeBack: .importedAccount(id:))` 续期）。
  - 主账号：`AppState.fetchCodexResetCredits()`，与前者对称，用主账号 token（PAT 直接用令牌，OAuth 账号 `writeBack: .codexAuthJSON` 续期），`accountId` 取 `codexAccount.accountId`（PAT 传 nil）。
  - 两者都不接入 backoff / inFlight 状态机，也不做「镜像默认账号」优化——每次展开都用对应账号自己的 token 独立请求。
- 展示：主账号行与导入行复用同一份 UI 组件 [`CodexResetCreditsDetailView`](../Settings/CodexResetCreditsDetailView.swift)（`CodexResetCreditsState` 三态：loading / success / failure），显示 `available_count` 汇总 + 每条 credit 的 `title`/`status`/`expires_at`（本地时区，`DateFormatter` 默认 `.current` 时区自动换算）。

### 14.8 展示层去重

同一 Codex 账号同时是「当前 CLI 登录（默认槽）」和「已导入副本」时，纯展示界面按身份去重，只显示一次；设置页作为管理界面不去重（见 §14.1）。

- 判据：`AppState.importedCodexAccountMirrorsPrimary(_:)`（`internal`，供展示层共用）——`chatgpt_account_id` 相等，且 `chatgpt_user_id` 相等或有一方缺失。
- **Popover**（[PopoverRootView](../MenuBar/PopoverRootView.swift) + [OtherCodexAccountsSection](../MenuBar/OtherCodexAccountsSection.swift)）：主 Codex 卡片会展示时（`includesCodex`），「其他账号」分区传 `dedupPrimary: true` 隐藏镜像项；PopoverRootView 用去重后的计数决定分区与其前置 Divider 是否渲染，避免悬空分隔线。Codex 服务被关闭走 `!includesCodex` 分支时**不去重**，避免唯一账号整体消失。
- **统计页**（[StatsView.timelineSections](../Main/StatsView.swift)）：主账号时间线段标题为 `Codex`（不再出现「主账号」字样）；仅当主账号段已展示时，跳过与它同身份的镜像导入段。历史存储 key 不变，被隐藏项的历史仍在盘上，只是不展示（身份随 CLI 切号漂移）。
